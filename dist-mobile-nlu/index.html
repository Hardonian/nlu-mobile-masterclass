01 / Frame the problem

Start with the user’s job—not the bot’s intent list.

A useful conversation has a bounded outcome, a legitimate data path, and a graceful exit. “Answer everything” is not a product requirement.

DETERMINISTIC TASK

Change an address

Authenticate, collect an order reference, validate the edit window, confirm, then execute through an authorised system.

GROUNDED KNOWLEDGE

What is your return policy?

Retrieve from approved policy sources, provide the relevant constraint and source context, and abstain when evidence is weak.

HUMAN / SPECIALIST

I was charged twice

Protect the customer. Avoid diagnosing from partial context; authenticate and route to the right support path.

Design principle: confidence is evidence about a classifier, not permission to take an action or invent an answer.

State inventory

  • What is known and where did it come from?
  • What is missing, optional, or unsafe to request?
  • Which API validates each claim?
  • What happens when the user changes their mind?

Exit inventory

  • Success with a receipt or next action
  • Clarification with a concise repair prompt
  • Fallback to grounded information
  • Escalation with preserved context, subject to privacy policy

04 / Design input

Mobile input is noisy, brief, and often interrupted.

Write useful examples

Cover the vocabulary and decisions your service supports: “return my shoes,” “send this back,” “can I get a refund?”, not just a long list of near-duplicates.

Include terse phrasing · date/order ambiguity · corrections · supported locales

Ask one good repair question

Weak: “I didn’t understand.”

Better: “I can help with an existing order or explain the return policy. Which do you need?”

Offer an escape hatch after repeated failure; never trap the person in a retry loop.

Prompt quality check
  • Can it be scanned in under five seconds?
  • Does it explain why sensitive information is needed?
  • Does it make a valid response easy to give?
  • Can a screen reader convey the same information and control labels?

05 / Route safely

Use a policy, not a single threshold.

Routing combines NLU evidence, missing fields, user risk, retrieval evidence, backend response, and conversation history. A 0.60 score can be a useful learning control—but not production governance.

1. Deterministic path

For actions and account data. Validate identity and required fields server-side. Confirm before non-reversible changes.

2. Grounded knowledge

For documentation-backed questions. Retrieve approved chunks, provide source context, and say when the answer is not supported.

3. Clarify or hand off

For high-risk topics, low evidence, recurring failures, policy exceptions, or user preference. Keep the reason observable.

Guardrail: never use a retrieval answer to authorize a transaction, establish identity, or make a high-impact decision. The transactional backend owns those decisions.

07 / Measure release
Accuracy is a diagnostic. Outcomes are the release decision.
Task success
Did eligible users complete the intended action correctly? Segment by journey, locale, device, and entry channel.
Safety & quality
Track unsafe-answer rate, invalid action attempts, retrieval support rate, correct escalation, and repair loops.
Experience health
Watch containment, abandonment, p95 end-to-end latency, backend failures, and accessibility defects.
Evaluation set starter
For each journey, write examples for canonical wording, paraphrase, short/mobile wording, misspelling or voice-like transcription, incomplete data, ambiguous data, unsupported request, adversarial/policy-bypass wording, and dependency outage.
